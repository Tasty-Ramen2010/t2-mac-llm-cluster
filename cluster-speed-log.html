Reading the prompt

Prompt reading speed went from 24 to 62 tokens/s for DeepSeek and from 11 to 53 for gpt-oss. The biggest steps were tensor parallel, 16-bit sync messages (half the bytes on the cable), and the new 5-bit kernel (+13%).

Every kernel is within ~10% of what the memory can deliver. What's left is the overhead around them (about 1,100 small operations per word, each ending in a thread sync) and the 54 network syncs. Moving more work to node2, using node1's 4th core, reserving huge pages, and a smaller shared-expert format all measured no better, which confirms the memory limit.
The long-chat fix

Why chats got slower, and the kernel that fixed it

In DeepSeek, Mellum and gpt-oss, groups of 8 attention heads share one stored row per past word. llama.cpp's CPU code handled each head separately: it read and converted every stored row 8 times, and kept its running total in 16-bit numbers. Our kernel converts each block of rows once, scores all heads together with one register per head, and keeps totals in 32-bit.

Next

Faster links and more Macs

The kernels are close to the memory limit, so the next real gains come from the link between Macs.

  1. One Thunderbolt 3 or 4 cable between node1 and node2. Linux networking over Thunderbolt runs at 10–20 Gbit/s instead of 1. It is prepared: tb-link.sh up brings the link up and start-ep.sh uses it automatically. Expected: syncs cost less than half, prompt reading +10–15%.
  2. A third and fourth Mac. Each Mac mini has 4 Thunderbolt ports, so four Macs can be wired directly to each other with no switch. Splitting every weight four ways halves each Mac's reading work (DeepSeek: ~410 MB per word each). Our sync code is written for 2 Macs today; it needs a 4-way version, which can be tested properly once the Macs arrive.
  3. For a classroom, pairs of Macs each serving their own users give more total answers per minute than one big group.
